# ADR-0004：仓库内长期知识资产与运行时快照

- 状态：accepted
- 日期：2026-07-25

## 背景

AiStu 的标准知识库包含来源快照、结构化语料、authoring、Schema、关系、
审查记录、标准知识对象、维护流水线和派生 RAG 索引。它是需要长期演进和审计的核心
产品资产。若只保存在开发机相邻目录，应用仓库无法独立恢复知识来源、验证派生产物，
也无法保证发布 commit 与知识版本一一对应。

另一方面，Electron 运行时只需要经过发布和校验的检索数据。把草稿、内部来源映射、
审查材料、Prompt 和维护脚本全部装入桌面应用，会无谓扩大包体与运行时数据暴露面。

## 决策

- 把完整 ODS 来源与标准知识内容域纳入 `content/ods-material/`，与应用代码在同一
  Git 仓库和 commit 中版本化；
- 保持知识、社区、用户学习和会话状态的数据域隔离，不因物理上同仓而混用模型；
- 排除 `.venv`、缓存和其他可重建的机器环境；
- 开发环境默认读取
  `content/ods-material/knowledge_base/rag/chunks.jsonl`；
- `AISTU_KNOWLEDGE_BASE_PATH` 只作为开发和 CI 的显式覆盖入口；
- 桌面包只携带同步后的
  `apps/desktop/resources/knowledge_base/rag/chunks.jsonl`；
- 打包前必须验证权威知识、同步快照并检查二者完全一致。

## 后果

优点：

- 克隆一个仓库即可恢复应用、知识来源、审查证据和维护工具；
- 发布 commit 能准确对应知识版本；
- 知识流水线和桌面引用合同可以在同一质量门中校验；
- 桌面运行时仍保持最小、只读和可审计。

代价：

- 仓库体积增加，需要明确区分权威源与派生产物；
- 知识改动与应用改动共享发布节奏，需要更严格的审查范围；
- 维护者需要 Python 环境运行知识流水线，但该环境本身不进入版本库。

## 被否决方案

- 继续使用开发机相邻目录：不能保证长期保存、可复现构建和 commit 对应关系；
- 只提交 `rag/chunks.jsonl`：保留了运行结果，却丢失来源、authoring 和审查链路；
- 把完整知识目录装入 Electron：运行时不需要这些内部资产，并扩大暴露面；
- 使用 Git submodule：仍增加初始化和版本同步成本，当前单产品阶段没有足够收益。
